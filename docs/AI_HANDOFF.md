## Архитектура и важные правила

- React 19, Vite 7, TypeScript; обычный адаптивный CSS и локальный Geist.
- `src/api.ts` вызывает только `Telegram.WebApp.Serverless.call()`.
- `tgcloud/endpoints/` и `tgcloud/handlers/` выполняются в Telegram Serverless.
  В этом runtime доступны только `sdk`, `sdk/db`, стандартный JavaScript и свои
  `.js` модули с относительными импортами. Express, Prisma, Node API и npm запрещены.
- SQLite объявлена в `tgcloud/schema.js`. Production не использует моки,
  localStorage или браузерные таймеры для отправки сообщений.
- Endpoint берёт владельца только из проверенного `ctx.initData.user.id`.
  Handler берёт отправителя из Telegram `message.from` / `callback_query.from`.
  Клиентский userId никогда не определяет владельца. Все запросы имеют owner scope.
- `.tgcloud/` — состояние и credentials CLI. Не читать, не редактировать,
  не коммитить. Авторизацию проверять штатными командами CLI.

## Реализованное поведение

Два раздела: «Задачи» и «Напоминания». Есть профиль, CRUD, статусы, пагинация,
счётчики, загрузка/ошибки/пустые списки, подтверждение удаления и сохранение в SQLite.
Дедлайн выбирается календарём с месяцем/годом и двумя вертикальными колонками
часов/минут, как в iPhone. Есть «Сегодня» и «Завтра».

Задачи могут иметь дедлайн и уведомление заранее. Самостоятельные напоминания
могут повторяться ежедневно, через день или по выбранным дням недели.
Предупреждение: в момент события, за 5/10/15 минут, час, день или свои 0–10080 минут.
Дата в форме — время события; `reminderMinutes` задаёт опережение уведомления.

Задачи и самостоятельные напоминания используют одну таблицу `tasks`.
Приватный серверный `request_key` отличает напоминания префиксом `reminder:`;
клиентский requestId исключает двоеточия. Фильтрация учитывает владельца и тип.
Две последние добавленные колонки `recurrence` (SDK JSON) и
`last_reminder_due_at` уже применены к production; повторная миграция не нужна.

`lib/recurrence.js` сохраняет IANA timezone, исходную дату и минуту дня.
Циклы идут по местному времени с учётом DST: разрыв сдвигается вперёд,
при повторяющемся часе выбирается ранний момент. «Через день» сохраняет исходную
дату даже при переименовании. После задержки отправляется одно ожидающее
уведомление, затем назначается будущая дата без потока пропущенных циклов.
История показывает последнюю доставку каждой серии; активная серия также
остаётся в ожидающих. Это не отдельный журнал всех доставок.

Повтор через 10 минут у цикла создаёт идемпотентную разовую копию, сохраняя цикл.
Удаление серии отменяет её копии. Старые кнопки проверяют timestamp события.
Обычное разовое напоминание переносится в той же записи.

Основная логика: `lib/task-service.js`, `lib/reminder-service.js`, `lib/recurrence.js`,
`lib/reminders.js`; формы: `ReminderForm.tsx`, `ReminderTiming.tsx`, `RepeatFields.tsx`.
Все endpoints и команды перечислены в README. `/start` обновляет меню команд;
`/remind` открывает форму, `/reminders` показывает списки в том же боте.

## Как работают сообщения при закрытом Mini App

`.github/workflows/task-reminders.yml` в `main` запускает официальный CLI через
`scripts/run-reminders.mjs`. Cron: `2-59/5 * * * *`, примерно раз в пять минут.
Обработка SQLite и отправка через Bot API выполняются на Telegram Serverless.
Это внешний запуск CLI, а не собственный backend или встроенный Telegram cron.
У платформы такой cron не документирован. GitHub может задерживать запуск;
точность до минуты не обещать, публичные workflows также имеют политику неактивности.

Actions использует secret `TGCLOUD_TOKEN` для app8347651382; его значение здесь
не хранится. `lib/reminder-config.js` содержит `remindersEnabled=true`.
`processReminders` требует служебного поля `maintenanceJob` в root developer ctx;
из публичного клиентского input оно не принимается. Worker использует lease,
версию расписания и проверяет отмену/удаление перед отправкой.
Bot API не гарантирует exactly-once при потере ответа после отправки; обычные
параллельные запуски защищены, абсолютную гарантию обещать нельзя.

## Что проверено и чего не считать доказанным

Последний `npm run check`: 34 backend-теста на реальной локальной SQLite,
ограничения runtime, TypeScript и Vite build. `npm run test:ui`: 8 сценариев,
официальный WebApp SDK с тестовым транспортом, обе темы, включая ширину 320 px.
В production проверены schema sync, webhook, все 9 файлов по HTTP/SHA-256,
отклонение неподписанных запросов с 401 и реальный запуск worker из GitHub.
Доставка напоминания по задаче ранее подтверждена пользователем.
Несколько суток циклической доставки в реальном чате не проверялись;
расчёт следующих циклов и DST проверены тестами и readonly CLI-пробой.

## Доступ и разрешения в новом чате

Новому ИИ нужен доступ к checkout или репозиторию. Credentials не переходят
в другой workspace вместе с Git: если штатный CLI не связан с ботом, требуется
`npx tgcloud login` с CLI Access, введённым пользователем через безопасный ввод.
Работающий GitHub secret не позволяет извлечь его значение для нового окружения.
Не просите прислать токен в публичный файл/commit и не копируйте его из старого чата.

В прежней сессии пользователь разрешил публикацию в marsen5689 и отдельно
последнюю миграцию двух полей; обе операции завершены. Исходное правило:
«Не выполняй публичный деплой и миграции базы без моего разрешения».
В новой сессии учитывайте явные разрешения пользователя; при согласованном
действии не запрашивайте их повторно. Новую миграцию сначала довести до
проверенного конкретного diff, затем согласовать её применение.
